# Research: 038 变异注入违规评测集 — 规则可变异性分析

**Date**: 2026-08-21
**Input**: KB v5 `references/01_负面清单检查/`（52 条规则）、037 触发规格、`ProductTags` 标签体系

## 1. 数据源盘点

负面清单四个文件共 52 条检核规则，每条含元数据：`原序号`、`适用标签`（如 health,medical,short_term）、`适用标签语义`、`检查要求`、`条款主题`（部分）、`风险触发标签`（部分）。

| 文件 | 规则数 | 特征 |
|---|---:|---|
| 产品责任设计 | 25 | 几乎全部为"不得包含/不得设计为"型，插入类变异的富矿 |
| 产品条款表述 | 21 | 混合型：禁止表述 + 义务要求（"应当/需"）+ 模糊要求 |
| 产品费率厘定及精算假设 | 5 | 混合：概念禁止 + 数值（2年交）+ 义务（区分社保定价） |
| 其他检查 | 1 | 单条 |

## 2. 规则可变异性分层

### Tier A：插入型（"不得包含/不得引入 X"）— v1 主力，约 15-18 条

变异算子 = 向宿主文档的指定位置插入违规概念/表述。规则元数据中的具体禁止词（账户管理、保证利率、终身给付限额、连续投保、火化证明、客票存根…）可直接复用为插入内容。

代表规则（原序号）：
- 22：分红险条款包含"账户管理/保证利率"→ 向分红宿主插入万能概念段
- 27：定期寿险含意外伤残可选责任 → 插入可选责任条款
- 28：疾病保险含生存金给付责任 → 插入生存金条款
- 29：护理保险含一般身故责任 → 插入身故责任段
- 30：失能收入损失险含意外身故责任
- 47：短期健康险引入"终身给付限额/连续投保" → 词组级插入，与封闭词组扫描能力直接对耦
- 7/8：意外险要求客票、寿险要求火化证明 → 在申请材料清单中追加不合理材料
- 9：第一受益人为贷款发放机构
- 10：等待期症状作为免责依据 → 改写免责条款

**注意**：插入位置有讲究——必须插入到条款主题正确的块（如生存金插入保险责任段），否则引擎可能因路由不到而"合理地"漏检，金标就会错。宿主条款块的 `clause_topics` 标签可用于定位。

### Tier B：数值越界型 — 约 4-6 条

变异算子 = 修改条款中的数值使其越过监管阈值。阈值来源不在负面清单本身，而在 037 触发规格与其他法规（健康险管理办法等）：
- 49：长期险交费期含 2 年交 → 把"10 年交"改为"2 年交"
- 等待期/犹豫期越界（依托法规 chunk 中的阈值，非负面清单条目）
- 免赔额过高/赔付比例过低（原序号 26：阈值模糊，需精算确认，v2 再做）

### Tier C：义务缺失型（"应当/必须/需"）— 约 6-8 条

变异算子 = 删除宿主中已有的合规表述：
- 2：删除减保权/续保权说明
- 4：删除管辖法院参照《民事诉讼法》提示
- 5：删除社会医疗保险参照《社会保险法》提示
- 6：删除生存证明形式解释
- 51：把万能险"允许追加保费"改为"仅可趸交"
- 50：删除定价区分社保/非社保表述（可能需要改费率表，v2）

前提：宿主文档中**必须已有**对应合规表述才可删除——宿主筛选时需验证（可用现有引擎抽取事实或 grep 检查）。

### Tier D：模糊表述型 — v1 排除，约 4-6 条

"表述应当严谨""前后一致""不得存在误导隐患"（原序号 1、3 等）：无客观判定标准，变异后金标本身有争议，留给 B 子集（真实通报案例）覆盖。

## 3. 汇总

| 层 | 规则数 | 变异类型 | v1 取舍 |
|---|---:|---|---|
| A 插入 | 15-18 | 违规表述插入 | ✅ 全做 |
| B 数值 | 4-6 | 数值越界 | ✅ 做阈值明确的 |
| C 删除 | 6-8 | 关键句删除/改写 | ✅ 宿主有对应表述的 |
| D 模糊 | 4-6 | — | ❌ v1 排除 |

**v1 可交付 ≥30 个变异算子，满足 spec US1 目标**；60 条确认上限下，3 份宿主每份打包 2 份变体文档（各 8-10 个变异）+ 少量单变异样本。

## 4. 宿主选择约束（关键发现）

规则的 `适用标签` 必须与宿主产品 `ProductTags` 匹配，变异才有意义：

| 宿主 | 匹配标签 | 可用 Tier A 规则（示例） |
|---|---|---|
| 医疗险（如 real-0xx 费率可调医疗） | health,medical,short_term? | 47（若短期）、26、9、10 |
| 重疾险 | health,disease | 28（生存金）、10、7 |
| 意外/护理/失能险 | accident / nursing / disability_income | 29、30、对应申请材料类 |

**结论：宿主扩为 9 份**（2026-08-25 定），按适用标签互补选择：分红两全、万能团体护理（双覆盖 universal+nursing）、费率可调医疗（联动 037 费率触发规格）、长期重疾、短期团体医疗、失能收入损失、意外伤害、长期补充团体医疗、终身护理。合计可承载约 37 条规则、30+ 算子。已知缺口：life,term_life 类规则（2 条，原序号 27 等）因 23 份产品中无定期寿险，v1 无法覆盖，v2 补宿主。

## 5. 与现有引擎的接口

- **变异定位**：复用 doc_parser 的条款块切分 + `clause_topics` 注册表（`load_clause_topic_registry`）定位插入/删除目标块；
- **金标结构**：直接复用 `RegulationAuditDecision` 语义（预期 violated + 法规依据条款块引用）；
- **指纹冻结**：复用 KB 构建清单 SHA-256 机制（`kb_build_identity.json` 同款做法）；
- **评测执行**：条款块级变异走 `audit_pipeline` 的现有入参（跳过 doc_parser）；原文档级变异走完整 `run_audit_pipeline`；
- **指标落点**：接入 `eval_snapshots` 表，指标计算新建 `lib/eval` 合规结论指标模块（现有 recall@k 不动）。

## 6. 风险

1. **插入位置不当导致"合理漏检"**（变异本身不构成真实违规场景）→ 人工确认环节显式检查"该变异是否会被合规审核人员认定为问题"；
2. **打包变异互相干扰**（如删除管辖提示与插入生存金改写同一块）→ 打包时按条款主题互斥分组；
3. **金标预期"其余规则维持原判定"可能不成立**（变异引发连锁误报）→ 指标定义中"漂移"单列，不视为金标错误，作为额外发现记录。

## 7. 对 plan 的输入

1. 算子库 schema：`operator_id, rule_ref(原序号+文件), tier, host_tags, target_topic, mutation(payload), expected_decision`；
2. 变体文档构建器：宿主 × 打包计划 → 变体文档 + 变异清单（JSON，含 diff）；
3. 确认清单格式：CSV/JSON，三行对照 + 确认字段；
4. 评测 runner：变体文档 → pipeline → 与金标比对 → 逐规则漏检率（双口径）报告。
