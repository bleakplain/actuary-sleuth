# Spec: 038-adversarial-violation-benchmark（变异注入违规评测集）

**Date**: 2026-08-20
**Status**: Draft — 待评审
**Input**: 037 执行报告（在线验证缺口）、规则引擎重构验收表、负面清单 100 条、KB v5

## 1. 背景与问题

- 引擎的最终合规结论质量目前无法量化：`lib/eval` 指标（recall@k/precision@k）只评检索层，OPT-001 要求的"逐规则精确率/召回率"未建立；
- 23 份真实产品（real-001~023）基本为合规成熟产品，只能测**误报率**，测不出**漏检率**（该报的违规没报）；
- cutover 门禁中 `EVALUATION_DATASET_STATUS="pending"`，需要可签收的评测资产；
- 每次引擎迭代（检索/抽取/LLM prompt 变更）无回归基准，"改好 A 坏了 B"无法发现。

本 spec 只覆盖评测集的 **C 子集：基于规则反向变异注入的违规样本**。A 子集（真实合规产品的误报率评测）复用 real-001~023，B 子集（监管通报/历史退回的真实违规件）暂缓——素材暂不可得。

## 2. 核心思路

每条监管规则天然定义了"怎样构成违规"。从负面清单规则 + 触发规格阈值**反向生成变异算子**，对合规条款文档做受控编辑，注入违规内容，再经人工确认"确实构成违规"，形成带金标的违规评测样本。

```
变异算子库（由规则反向派生）
→ 选择宿主产品与宿主条款块（确保变异前该处合规）
→ 应用变异（数值越界 / 关键句删除 / 违规表述插入 / 义务缺失）
→ 人工确认（变异确实构成违规、且仅构成目标规则的违规）
→ 冻结为评测集（版本 + 指纹）
→ 引擎跑评测 → 漏检率 / 误报率 / indeterminate 率报告
```

## 3. User Stories

### US1：变异算子库
作为规则维护者，我能为每条可机检的监管规则定义至少一个变异算子，使得对合规文档应用该算子后文档违反该规则。
- 算子类型 v1 限定四类：**数值越界**（等待期 90→200 天）、**关键句删除**（删犹豫期全额退保句）、**违规表述插入**（收益承诺式表述）、**义务条款缺失**（删除整段）。
- 算子与规则 ID 双向关联，可追溯到法规依据。
- 验收：优先覆盖已配置触发规格的规则 + 负面清单中关键词/正则可机检的规则；v1 目标 ≥30 个算子（覆盖约 30 条规则），每一算子有单测。

### US2：宿主选择与变异执行
作为评测构建者，我能对 real 产品应用变异算子，产出变异文档与**逐规则金标**（预期该规则应判 violated，其余维持原判定）。
- v1 范围：**9 份宿主产品**（分红两全、万能护理、费率可调医疗、长期重疾、短期团体医疗、失能收入损失、意外伤害、长期补充团体医疗、终身护理——覆盖负面清单全部适用标签类别，除 life,term_life 因无对应产品暂缺），每份打包 1-2 份变体文档，总变异条目 ≤60。
- 变异只改条款文本，不改文档结构；产出物包含：变异文档、变异清单（规则 ID、宿主条款块 ID、变异类型、改动 diff）。
- 验收：变异文档能被现有 doc_parser 正常解析，且改动 diff 完整可审计。

### US3：人工确认工作流
作为审核负责人，我能对每个变异样本做轻量确认（是/否构成目标违规、有无误伤其他规则），确认结果与确认人、时间一并冻结。
- 确认界面对象为变异清单条目（非全文档），单条展示"条款原文 → 变异后文本 → 目标规则"三行对照，单个确认预计 <1 分钟。
- 确认人为主项目负责人本人（非独立精算师），因此 v1 严格控制确认总量：**MVP 确认条目 ≤60 个，预计总耗时 ≤1 人日**；超出部分顺延到 v2。
- 验收：未确认样本不计入评测集；确认记录含确认人、时间、结论三字段。

### US4：评测执行与指标
作为引擎开发者，我能一键对冻结的评测集跑审核管线，产出报告：逐规则漏检率（应 violated 判成 satisfied）、漏警率（判成 indeterminate/manual_review 的比例）、变异无关规则的判定漂移（回归检查）。
- 指标按规则 ID 和变异算子类型分组。
- 验收：MVP 跑完产出完整指标报告；同一评测集两次运行结果可复现（LLM 温度等参数冻结）。

### US5：回归基线
作为引擎维护者，引擎迭代后我能用同一评测集对比前后版本指标，输出增量报告。
- 验收：接入现有 eval 快照机制（`lib/eval` snapshot），不新建独立评估体系。

## 4. 范围外（Out of Scope）

- B 子集（真实违规样本）与 A 子集金标化（real 产品的人工逐条金标）；
- 变异算子对 PDF 宿主的格式保真（v1 宿主限 docx/doc）;
- 通用对抗样本生成（LLM 自动变异）——v1 算子全部手工/脚本派生；
- cutover 门禁的正式打开（评测集是必要条件之一，不自动触发切换）。

## 5. 关键设计决策（已定，2026-08-21）

1. **变异层级：双轨** — v1 以条款块级变异为主（快速建集、迭代算子），建集稳定后补充小批量原文档级变异，验证 doc_parser 对变异文档的解析表现；
2. **打包策略：每文档打包 5-8 个互不冲突变异** — 按规则不相关原则打包，报告时按规则拆分归因；另留约 10% 单变异单文档样本，用于漏检个案的复现定位；
3. **指标口径**：漏检率双口径并报——严格口径（indeterminate/manual_review 计为漏检）与宽松口径（仅 satisfied 计为漏检），此即三值保守判定权衡曲线的数据来源；
4. **资产化标准：按可对外发表规范设计** — 数据结构对齐学术评测集惯例（版本化、指纹冻结、指标定义成文、方法可复现、变异算子与法规依据显式关联），条款文本版权与公开化问题暂不处理，但数据 schema 不排斥未来脱敏公开；
5. **人工确认**：项目负责人本人执行，MVP 确认量硬上限 60 条 / 1 人日。

## 6. Constitution Check（gen-plan 前置）

- Library-First：复用 doc_parser、audit_pipeline、lib/eval snapshot、KB 指纹机制
- 测试优先：算子单测 + 变异 diff 校验 + 指标计算单测
- 简单优先：v1 手工算子、3 份宿主、不做 LLM 自动变异
- 显式优于隐式：金标与规则 ID、确认人、指纹显式绑定
- 可追溯性：US1-US5 → 本 spec §3
- 独立可测试：每个 US 独立交付
