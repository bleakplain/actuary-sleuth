# 法规 QA 质量与延迟优化计划

日期：2026-10-16。状态：调研与方案，尚未执行本计划、未切换模型、未修改线上服务。代码基线为 `qa-chat-fluency-20261013` 候选工作区；实际证据来自 2026-10-15 的原入口请求，不冒充今天重新跑出的性能结果。

输入：[本轮调研](research.md)、[既有执行记录](../qa-chat-fluency-20261013/tasks.md)、[既有 QA 规格](../038-professional-regulatory-qa/spec.md)。本轮沿用问题驱动模式；不为写计划创建新工作区、提交或推送代码。

## 1. 决策摘要

建议从“自由生成长答案 → 用大量规则审核 → 同一模型重写 → 仍不通过则贴原文”，转为“组织完整且有区别的证据 → 一次生成带证据绑定的简明答案 → 按风险处理少量争议”。

优先做四件事：

1. 修复系统性表格解析和证据覆盖丢失；相似度最高不等于回答所需材料齐全。
2. 将可证明的事实冲突与启发式疑点分开；保留必要安全校验，撤掉未经验证的词面一票否决。
3. 缩短初稿与修订，让一次生成尽可能成功；同证据比较现模型和候选模型，不默认把“免费”与“高性价比”画等号，也不预设换模型一定有效。
4. 用少量经确认的典型问题校准，自动扩展回放；不先建大型本体，不手工逐条整理整本手册。

原文兜底继续保留，但只计为“检索参考交付”，不计为成功的综合问答。专业问答与正式法规审核是不同承诺：QA 不冒充现行效力鉴证，合规引擎也不受本轮放宽 QA 交付策略影响。

## 2. 本地已确认问题与边界

### 2.1 33 秒花在两次写答案，而不是两次语义核对

原入口消息 821，问题“死亡保额有什么规定”，trace 总耗时 33.250 秒；HTTP 回放报告 33.263 秒。

| 环节 | 耗时 | 观察 |
| --- | ---: | --- |
| 问题解释 | 1.473 秒 | 输出解析失败，回退原问 |
| 检索 | 1.089 秒 | 内含 RRF 约 0.132 秒、BGE 约 0.719 秒，子步骤不能重复相加 |
| 初稿生成 | 15.411 秒 | 一次模型调用 |
| 定向重写 | 14.905 秒 | 又一次模型调用 |
| 其他 | 约 0.37 秒 | 校验、编排及保存等余量 |

该请求共 3 次 LLM 调用，语义证据判断 0 次。早先其他请求确实出现过语义核对超时，但不能套用到本请求。约 91% 的耗时在两次生成中；单独优化向量数据库或继续增加校验超时不是当前首要解法。

证据：`outputs/qa-entry-20261015/death-fix-smoke.json`；原 SQLite 中 message 821 的 trace。这里只是一个真实失败案例，不是总体 P50/P95。

### 2.2 找到了资料，但最终证据包覆盖失衡

trace 中检索早期出现未成年人死亡保额限制，后续 top-k/重排与邻块扩展没有把它保留到最终生成上下文。最后 9 段里有 6 段来自司法解释及其附带材料，重复度高，而问题涉及的不同规则维度没有均衡覆盖。

现有 `rag_engine.py` 的 RRF+BGE 不是缺失项，应改其候选保留、去重和上下文组装。当前邻块只解决局部连续性，不能证明概览问题的覆盖充分性；补检索再用原问题也不等于补到已识别的缺口。

### 2.3 校验存在误拦，也确实拦住了错误，不能全部关闭

只用消息 821 的来源 4 做离线检查：保留产品范围、分母、到达年龄、比例下限及各档数字的忠实表格释义，仍可能触发 `anchor_value_mismatch`、`condition_mismatch`、`quantifier_mismatch`、`entailment_unresolved`。相邻词锚、条件词和量词标签不一致未必构成逻辑矛盾。

`repair.py:440–446` 只允许三类软错误进入语义判断；一旦混有其他启发式错误或无引用片段，整组语义判断跳过，转向重写。`attribution.py` 还可能把“规定如下”这类引导语当作无引用主张。

但本次真实草稿也有无效引用和不当混合例外的内容，不能将所有失败归因于验证器。正确方向是校准阻断依据，不是忽略错误后直接展示草稿。

可直接建立回归的忠实释义（只用于复现当前库内表格，不声明其现行效力）：

> 保险公司开发销售的个人定期寿险、个人两全保险、个人终身寿险和个人护理保险产品，死亡保险金额或护理责任保险金额与累计已交保费或账户价值的比例下限按到达年龄分为：18－40周岁160%、41－60周岁140%、61周岁以上120%。[来源1]

复现方式：将上述句子与消息 821 的比例表来源独立传入 `parse_citations`；再构造改错百分比、删产品范围、下限改固定值的反例，比较误拒与错误放行，而不是只要求前一句通过。

### 2.4 表格后正文黏连是上游系统性缺陷

2016 精算通知的源 Markdown 第 45 行为 `| 61 周岁以上 | 120% |其中，到达年龄……`，定义紧贴表格行。原文虽然存在，GFM 展示时仍可能遗漏，引用存在不等于用户看到了完整条件。

直接原因：`docx_to_md.py:746–754` 保存表格后，下一段普通正文可被拼到前一块末尾；后续格式化又把整行当表格。全库初筛找到 32 行、15 文档疑似同类情况，是待核对候选数，不是全部已确诊数。应修块类型边界并自动重建，不逐页人工修补。

另有来源归属混杂：消息 821 中收录保险法第三十四条的段落挂在“司法解释（三）”文件标题下。引用 ID 虽真实，法律名称和条号组合仍可能不对。需要区分编纂容器、实际法源、被引条文和编辑说明；这是摄入身份治理，不是给答案多加一个引用就能解决。

### 2.5 不能把手册收录状态当作现行法规证明

`/Users/plain/work/actuary-assets/kb-qa/v1/release_manifest.json` 共有 53 个收录文档记录；53/53 的原始 `legal_status=unknown`、`review_status=trial`、`official_url` 和 `effective_from` 为空，适用范围统一为“人身保险产品开发”。这描述元数据缺口，不表示 53 份法规全部无效，也不表示手册只有 53 个法律条款。

`temporal.py:300–304` 会将 `legal_status` 覆盖为计算出的时间/试用状态，并保留 `source_legal_status`。需要拆清三种状态：法规效力、资料审核/发布状态、查询日期匹配结果。不能因为 `trial` 被接受，就向用户宣称法律现行有效。

### 2.6 已有基础设施，不宜重造

- 已有混合检索、本地 BGE、QA 发布清单、请求级快照隔离、引用 ID、一次修订、SSE 进度和回放工具。
- 已有共享轻量本体：11 个产品概念、1 条试用批准的“重疾→疾病”关系。不是从零建设，也不是完整保险本体。
- 既有 3477 个后端测试、106 个前端测试通过是代码回归证据，不是法规答案准确率。
- 旧广覆盖回放有不少 `answerability=unknown` 的合成样本，程序 `verified` 状态不能用作人工正确金标。

## 4. 目标架构与交付策略

```text
原问＋必要会话槽位
  → 混合召回／本地重排
  → 去重、主题覆盖、补父条与表头表注，形成证据包
  → 一次生成：简明分项答案＋主张到证据的绑定
  → 快速检查
      ├─ 支持充分且无明确冲突：交付
      ├─ 释义/范围有疑点：批量语义核对
      ├─ 确定缺证据或草稿错误：最多一次定向补检索／修订
      └─ 仍未解决：可独立成立的部分答案＋明确缺口；必要时原文参考
```

### 4.1 证据包，而非不断加长的字符串

每份证据复用已有 ID、文档版本和发布清单，增加/完善：标题层级、正文块类型、条款/表格单元位置、适用主体、条件/例外、效力元数据来源。表格必须连同表头、单位、上下限和注释可见。

搜索文本可加入明确标记的上下文前缀；作为法律依据的原文保持独立、不可被生成摘要替换。AI 推断的标签只帮助召回，不自动升级为正式法条事实。

概览问题先保证不同规则维度的覆盖，再按相关性分配有限 token。用去重、文档/条款多样性和已知问句结构做首轮选择；复杂问题最多规划 2–3 个子查询，并行执行，原问检索始终保留。不为“死亡保额”硬编码一套专用答案。

候选数、每文档保留数、上下文 token 上限都作为离线实验参数，先测例如 20/40 候选、6/10 个最终证据单元，不直接把供应商某个 top-k 值当最佳实践常数。例外条款和父条在配额内成组保留，不能因去重误删。

### 4.2 一次生成承担答案组织，不再事后从任意长文猜主张

先做受约束的简短答案：结论、适用范围、关键数字/条件、例外、引用。概览可分多个场景，但不为了凑全覆盖而补造内容；缺失的维度明确写未确认。

试验在同一次生成返回小型结构化主张：`text`、`evidence_ids`、必要的 `scope/conditions`、`answer_gaps`，客户端渲染自然语言。字段只包含可核对结论，不索要隐藏推理过程。输出格式和引用有效仍不等于事实正确。

内部输出模型放在现有 `lib/common/models.py`，使用 frozen dataclass；LLM 解析复用 `lib/llm/`。服务端将经过检查的证据 ID 映射为本轮引用编号并渲染文本，首期 API/SSE 仍可返回现有自然语言 `answer`，不为了内部结构化强制全栈协议迁移。scope/conditions 如由模型提取，仍是待验证字段，重要条件必须出现在用户可见答案中。

与“简短 Markdown＋现有引用解析”做对照；只有结构化输出稳定、减少校验误报且总延迟更低时才采用。避免为了复杂 JSON 增加一个专门修格式的模型调用。解析失败可进行确定性规范化；不能信任模型声称的置信度。

### 4.3 风险分层，不是简单放松全部校验

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 可确定的约束违反 | 引用不存在、跨快照、来源权限不符；在相同主体/表格行/条件已对齐后，数字单位或上下限明确相反 | 硬拦该主张，定向修正；来源/权限问题阻断整条回答 |
| 结构或语义疑点 | 非逐字释义、邻近词锚不一致、条件词标签不同、分句可能不完整 | 软信号；结构对齐或批量语义检查，不能直接视为矛盾 |
| 证据覆盖不足 | 缺例外、只找到了其中一类产品、法条交叉引用没有目标条文 | 定向补检索；保留独立可回答部分，不概括成全产品规则 |
| 技术故障 | 超时、输出 JSON 无效、供应商不可用 | 与证据不足分开记录；降级参考或重试提示，不能放行未核实的高风险主张 |

校验以主张/证据组为单位。一个引导句或另一主张的格式问题，不应让所有可核对主张失去语义判断机会。普通非事实性的“以下分几种情况”不要求法规引用。

在线保留来源、关键数字、条件和适用范围的必要检查；风格、冗余、一般语义相似度评分移至离线抽检。高风险数值/适用范围在未核对清楚前不预先流出。初期仍先完成必要检查再交付正文，真实流式分段作为后续可选项，不用动画掩盖延迟。

### 4.4 调用预算

- 清楚的单轮问题不做独立模型改写；含指代/条件替换时才按需解析。
- 默认 1 次答案生成；有实质疑点时增加 1 次批量核对。
- 最多 1 次修订。若修订新增主张，仍要必要终检；不能为“最多两次调用”牺牲安全。总调用数、修订率和其真实成功增益必须报告。
- 同一次修订必须拿到明确错误位置或新增证据。再问一遍“请检查”不构成优化。
- 按阶段预留时限，当前协作式 deadline 不宣称能杀掉所有运行中线程。并发请求、取消和超时后资源释放应单独测试。
- 初期不加答案语义缓存；先修正确性。后续如使用缓存，key 必须包含 QA release、模型/提示/验证策略版本、时间/地区/产品槽位与权限范围，切版本立即失效。

## 5. 分阶段实施计划

估算为 1 名熟悉现有代码的工程人员、AI 辅助实现的工作量，不是交付日期承诺；总计约 8–12 个工程工作日，分两批交付。发现更多摄入问题或模型权限限制时另估，不无限延长同一个任务。

### P0：基线与上限定位（1 天）

对应 US2/US4。复用 `scripts/evaluate_rag.py`、`lib/eval/` 和现有 trace。

1. 冻结当前线上候选代码差异、QA release、模型 ID、提示版本、缓存状态；不把主仓库旧实现误作线上版本。
2. 从既有日志/fixtures 选 30 个锚定问题：20 个可回答、10 个缺资料/错误前提/时间或产品边界，覆盖等待期、保额、除外、续保、费率和产品设计。15 个调参、15 个封存，必须按原始问题族拆分。
3. 每题整理最小证据与关键结论/禁错项，先复用已审核资料和既有事实夹具；不要求专家写长篇标准答案。答案可回答性不能确定者保持 unknown，不计入准确率。
4. 为失败样本做“给足正确原文”的受控生成测试：若仍失败，优先模型/生成契约；若成功，优先召回/上下文；再对比验证前草稿与实际交付以定位误拒答。
5. 本阶段新模型外发需单独确认；无授权时先做现模型与离线校验对照。

交付：逐例错误归因、分阶段耗时/调用数/成本报告；先识别主因再决定后续参数。不得拿模型自评当金标。

### P1：修语料结构与证据覆盖（2–3 天）

对应 US1/US2。

文件：`lib/doc_parser/kb/converter/docx_to_md.py`、`lib/doc_parser/kb/md_parser.py`、`lib/doc_parser/models.py`、`lib/rag_engine/builder.py`、`rag_engine.py`、`corpus_manifest.py`、相关 `data/` 与现有入库/重建脚本。

1. 按段落/表格块类型禁止跨边界拼接；表前后保留空行；检测表列数、管道尾随正文、丢失表注和层级跳变。
2. 对 32 行疑似异常自动生成差异报告，优先确认已影响问题的文档；自动检测不等于全部确诊。保留用户此前指定忽略的第 316 页识别码，不重新纳入待修内容。
3. 将原始文档/章节/块位置等已有元信息传递到索引；一份编纂手册中被引用的法律与编辑说明不得仅因位置相邻被误认作同一法规条文。
4. 使用新 QA 候选版本重建，不原地改 v1 的签名文本。派生检索前缀与原文分离；元数据由规则优先提取，无法确认者保留 unknown。
5. 优化概览的去重和覆盖；对本问题验证早期召回的不同规则证据不在重排后全部丢失。添加“父条/表头/表注＋子条”成组选择，控制总长度。

交付与测试：表格后定义在 Markdown、前端可见文本和证据引用中均存在；固定参考集关键证据召回/保留率达门槛；QA/合规语料、版本和引用 ID 隔离回归通过。

### P2：短路径与校验重构（2–3 天）

对应 US2/US3。

文件：`lib/rag_engine/query_preprocessor.py`、`graph.py`、`rag_engine.py`、`attribution.py`、`repair.py`；`lib/llm/qa_interpretation.py`、`qa_evidence.py`、`qa_budget.py`；模型/常量复用 `lib/common/`。

1. 对明确问题取消无效前置解释；保留多轮槽位替换、原始问题和显式条件。
2. 试验简短分项生成与轻量结构化主张输出，限制重复引文和无关法条，不机械压成一句而丢范围。
3. 将启发式冲突分类为 soft/confirmed，按主张分别处理；只有明确对齐后的矛盾可硬判，语义判断不能覆盖真实数字/权限/版本冲突。
4. 改补检索输入为明确的缺失维度/交叉引用，而非总是重跑原问题；追加证据保持稳定 ID。已有正确主张修订时不全量改写，必要终检只核改变及受影响内容。
5. 原文参考不作为正常答案形态；能独立成立的支持项先整理为部分答案，不能通过删例外制造“已支持”句子。
6. 删除被替换且无调用的旧判断分支；迁移期策略用于同机对照，验收后收敛，不无限增加永久开关。

特别处理 `qa_evidence.py` 当前“超过 6 条直接空结果”和“一行无效则整批结果丢弃”：控制生成的主张粒度和批量 token 预算，逐项验证并保留有效证明；超预算和格式无效明确标为未完成。整体没答全不能抹掉确有证据的独立部分，也不能因此把部分答案冒充完整回答。日志保留可审计的改动主张与失败分类，避免只记录重写长度；遵循权限和最小化保留，不记录密钥。

交付与测试：忠实表格释义不误拦，错误比例/上限下限/产品范围/例外仍被拦；一般引导句不触发无引用错误；无证据、技术故障与真实矛盾分流正确；复杂问题不无界循环。

单测使用脱敏固定 fixtures，不依赖用户 SQLite、临时 trace 或外部网络；真实文件和模型调用只进入明确标记的集成/验收任务，失败数据保留而不改写历史成绩。

### P3：模型对照与交付体验（1–2 天）

对应 US2/US3/US4；可与 P1 的离线工作部分并行。

文件：现有 `lib/llm/factory.py`、供应商适配器与 `lib/config.py`，`api/routers/ask.py`、`api/schemas/ask.py`、前端 `MessageBubble.tsx`、`SourcePanel.tsx`、`types`、`askStore`。

1. 用同证据/同输出长度对照现 `glm-4-flash`、同供应商可用的当前免费候选、一个经批准的较强候选。免费候选是否存在、账号权限、速率及价格在执行时按官方文档/控制台确认；不在本计划预设某新型号免费。
2. 比较中文范围理解、表格释义、JSON/引用有效率、一次成功率、错误拒答率、P50/P95 和每个成功回答成本，而不只比较单次 token 价格。
3. 若现模型短路径已达标就保留；若正确原文给足仍系统性失败，则停止加词面规则，以模型能力实验决定是否升级。新供应商、付费模型或新的法规外发范围需确认。
4. 明确前端四种交付：完整解读、部分解读、原文参考、需要关键条件。注明基于库内资料的范围，避免每答堆满相同免责声明。
5. 流式只在不泄露未核对高风险主张、可保存一致消息且能处理中断/追问的前提下另行推进；本期速度主收益来自少重写，而不是打字动画。

### P4：灰度与发布收敛（2–3 天，含反馈修正余量）

对应 US1/US4。

1. 在独立数据库做完整 HTTP/SSE 验收，再接原入口；不改写既有用户失败记录。
2. 复用 `scripts/deploy.py` 统一管理 QA 子进程的启动、停止、健康、版本指纹与重启恢复，消除当前侧挂 54833 手工启动的运维缺口。保持合规配置与行为不变。
3. 核对历史列表、引用点击、表格可见文本、切换会话、连续追问和快照切换。后端全测、类型检查、前端测试构建完成后才能交付。
4. 试用比较失败分布，只有达到门槛才替换；保留前一 QA release/服务配置回滚，不回滚数据库覆盖新消息。
5. 线上 trace 最小化保留，受现有权限控制；不将私密问题/法规全文打包上传第三方评测，不保存密钥。

## 6. 最低人工成本安排

| 工作 | 自动完成 | 人工只做什么 | 首轮估算 |
| --- | --- | --- | ---: |
| 表格/层级质量 | 扫描、差异定位、自动重建、渲染一致性检查 | 判断少量无法确定的结构异常 | 0.5–1 小时 |
| 30 个锚定问题 | 从失败记录/现有 fixtures 草拟关键证据、结论与禁错项 | 确认可回答性及关键条件，不写标准长答案 | 1.5–3 小时 |
| 高频约 10 份法规元数据 | 搜索官方来源、提取候选日期和修订关系、整理差异 | 确认有歧义的版本/效力及适用范围 | 2–3 小时 |
| 分歧复核 | 自动聚类失败和评分分歧 | 只看未覆盖的新错误类型 | 0.5–1 小时 |

合计约 4.5–8 小时，分批完成；这是资料能找到官方证据且无复杂效力争议的估算，不是保证。复杂修订链另算，不强行压缩成每份几分钟的法律鉴定。每周约 20–30 分钟看高风险新增/异常可作为起步安排；法规大量更新时需增加投入。

如果只能投入 1–2 小时：先确认 15–20 个典型问题，发布“基于导入资料的体验试用”，其余继续自动检查；不宣称正式准确率或现行法规完整覆盖。省掉的是全库手工知识工程，不是把所有人工判断隐藏为模型自证。

共享本体只补高价值缺口：复用现有概念/别名与有依据的分类关系；保额/保险金额等语言映射可作为召回扩展。法律规则继承仍要检查产品、地域、时间、例外。候选关系自动提出，未经确认不进入合规的正式推理集合；QA 和合规库绝不合并为一个检索范围。

## 7. 验收目标：先限定范围，再谈质量

以下为试用目标，不是已实现成绩，也不是总体 95% 准确率承诺。

| 维度 | 试用门槛 | 统计边界 |
| --- | --- | --- |
| 锚定集有效解读 | 已确认可回答的 20 题至少 18 题正确回答关键点 | 原文粘贴、澄清、拒答不算完整成功；逐题列出错误，不只给百分比 |
| 误拒答 | 上述 20 题最多 1 题因系统原因拒答 | 回答不了不能从分母剔除 |
| 高风险错误 | 固定数字/范围/例外/历史/无资料反例中无已发现的关键错误放行 | 样本零错误不代表总体零风险 |
| 证据覆盖 | 必需证据 recall ≥95%；最终证据包中必需项覆盖率 ≥95%、所有必需项齐全的可回答题 ≥90%；本轮已知失败题不得丢失已确认必需项 | 证据单元含主句及其不可拆条件/例外；事先标记可替代的等价证据，按题宏平均，不能靠大段重复文本凑命中 |
| 普通问题延迟 | 成功可用解读 P50 ≤6 秒、P95 ≤12 秒，且先满足有效解读与误拒答门槛 | 固定机器/模型/快照、并发=1、缓存冷暖分开；另报所有请求的终止延迟，失败不得从该统计删除 |
| 复杂问题延迟 | 成功可用解读 P95 ≤20 秒，且先满足质量门槛 | 原文参考/拒答/澄清不算成功解读；另报全请求终止延迟，避免快速拒答拉低时延“成绩” |
| 反馈时间 | 首个真实进度 P95 ≤1 秒 | 单独报告，不代替正文速度 |
| 全链路 | 主题切换、时间/地区否定条件、跨库隔离、权限、引用点击与表格定义不丢 | 本地契约测试与真实 HTTP/UI 测试均要通过 |

自动派生 120–180 条口语/多轮变体用于回归，不将同一原题变体当作独立专家样本。代表性失败类型至少重复 3 次；调参集与封存集按问题族隔离。若反复看封存结果再调参，它就不再是独立验收集，需要补新问题。

30 题初始集合按每组 10 个可回答＋5 个边界题拆为调参与封存两组；上表的 20 题是完整锚定集的回归门槛，必须另报封存组至少 9/10 个可回答题关键点正确、无已发现高风险错误，不能只靠调参集拉高总分。10 个独立可回答题依然很少，只支持限定试用决策，不支持总体准确率认证。

报告同时列出：回答关键事实正确率、有据性、覆盖完整性、错误引用率、误拒答、部分/原文降级率、每阶段耗时、修订率、供应商错误、token/费用。模型评分只筛分歧；少量人工校准不能推导“95%已认证”。

## 8. 实验顺序与停止规则

1. 离线错误归因与已知正确原文实验；不先加新系统。
2. 固定模型，分别比较旧证据包和新证据包；确认必要证据保留的收益。
3. 固定证据，比较旧/新生成与验证策略；保留验证前草稿仅用于离线评分，影子验证不能把错误答案发给用户。
4. 固定证据与生成契约，再比较模型；全链路组合复测。不要一次改检索、模型、提示和样本集后声称知道收益来自哪里。
5. 迭代只看调参集与预设开发回归，保留质量收益且成本/延迟可接受的改变；冻结阶段候选后才做一次封存验收。封存失败若用于再次调参，必须补充新的独立验收题。重写若没有明显成功增益，缩减触发条件，不追加第三第四轮。

不做：全量 GraphRAG/图数据库、全书手工本体、微调新模型、全网在线补答案、默认每问多代理互审、未经批准上传 ima、无限循环追问模型。若将来真实失败集中在多跳关系或跨法冲突，再单独评估图检索，不预先付复杂度成本。

## 9. Constitution Check

- Library-First：复用既有 `lib/rag_engine/`、`lib/llm/`、`lib/doc_parser/`、`lib/eval/`；不新建 service 包或替换技术栈。
- 测试优先：每阶段有独立测试和固定真实回放；失败样本先建回归，再改策略。
- 简单优先：一次生成、按需核对、有限修订；重型代理和图数据库延后。
- 显式优于隐式：问题槽位、证据包、发布/效力/时间状态、错误分类和预算独立可观察。
- 可追溯：各阶段回溯既有 QA 规格 US1–US4；保留源文件、条款、版本与引用 ID。
- 独立可测：P1 可以只测摄入/检索，P2 以固定证据测生成校验，P3 固定输入测模型，P4 测部署与用户链路。

限制：本轮只有文档变更，不执行业务修复、不重建知识库、不修改 `.env`、不产生新模型调用费用。进入执行阶段先确认基线仍是上述候选工作区，保护已有未提交变更，并按权限确认新模型外发与预算。
