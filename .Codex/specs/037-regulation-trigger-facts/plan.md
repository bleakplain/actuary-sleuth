# Implementation Plan: 产品事实驱动的法规触发与动态证据检索

**Date**: 2026-08-07
**Status**: Implemented — 影子验证；生产排除待精算验收
**Input**: `research.md`、036 审核主链规格与 real-019 原型结果

## 1. Summary

在现有主链中增加可审计的法规触发事实，并用触发结果约束动态条款检索：

```text
文档结构解析
→ 一次性产品通用事实账本
→ 产品标签过滤法规
→ 汇总并去重候选法规的触发事实需求
→ 确定性提取 + 可选的单次批量 GLM 事实补充
→ triggered / not_triggered / indeterminate
→ 主题、事实、受控关系和带门槛文本检索
→ 按需扩大证据
→ 云端 GLM-4 最终法规判断
```

本计划不修改法规原文，不让旧 `rule_engine.py` 提供监管语义，不允许事实层直接输出合规结论。

## 2. Technical Context

**Language**: Python 3.14
**Existing modules**: `scripts/lib/compliance/`、`scripts/lib/doc_parser/pd/`、`scripts/lib/llm/`
**Retrieval**: 受控主题、BM25、现有 embedding/reranker
**LLM**: 最终审核继续复用现有云端 GLM-4；产品事实补充以可注入适配器实现，默认不自动外发
**Testing**: pytest、冻结真实产品验收表、离线模型桩
**Performance goal**: 法规候选数量不设上限，单份产品总截止时间15分钟；当前智谱账户最终判断并发2，到期未完成项明确标记incomplete。

## 4. 方案权衡

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 全确定性规则 | 用关键词、正则覆盖全部触发事实 | 快、可解释 | 无法穷举复杂表达，容易误判 false | 不采用 |
| B. 每法规 LLM 判断触发 | 每条法规单独让 GLM 读产品 | 实现直观 | 调用数接近翻倍，慢且不可审计 | 不采用 |
| C. 共享事实账本 + 按需 GLM | 通用事实一次提取，未决事实合并补充 | 可复用、可追溯、时间可控 | 需要触发元数据和验收集 | 采用 |

## 5. 核心数据合同

### 5.1 法规触发规格

求值器只保留有限运算符：`equals / exists / contains_any / less_than_or_equal`。Excel v1 对布尔事实只开放 `equals / exists`，对数值事实只开放 `less_than_or_equal`；`contains_any` 需注册字符串值事实后才开放。证明策略限于：

- `explicit_presence`：有明确正面证据；
- `explicit_negation`：有明确否定证据；对开放世界产品功能只用于路由和审核，第一版不单独据此排除法规；
- `controlled_classification`：来自受控且互斥的产品分类；
- `closed_phrase_scan`：封闭词表全文扫描；
- `numeric_fact`：带单位的数值事实；
- `semantic_fact`：规则不能确定时的语义事实。

每个法规条款单元保存：

```text
fact_name
operator
expected_value
target_topics
required_facts
proof_strategy
search_all_terms
search_any_terms
```

第一版不执行任意 Python 表达式，也不支持任意嵌套布尔逻辑。复杂条件拆成多个受控条件按 AND 求值，确有已验收需求后再扩展。

### 5.2 产品事实账本

每个事实保存：

```text
name
truth = true | false | unknown
value
unit
method
confidence
evidence(clause_id, quote)
reason
```

账本按产品审核请求生成一次，所有法规共享。

### 5.3 触发求值结果

```text
status = triggered | not_triggered | indeterminate
fact_names
reasons
evidence_clause_ids
```

只有 `not_triggered` 才停止该具体检查；`indeterminate` 必须保留法规。

## 6. 数据来源与治理

推荐在法规 Excel 增加受控列，作为精算维护源：

- 触发事实；
- 触发运算符；
- 触发期望值；
- 目标条款主题；
- 证明策略；
- 检索必含词组；
- 检索任一词组；
- 触发条件说明。

Excel 转换器把这些列编译进 KB metadata。空值表示“没有触发规格”，不是 false；未配置的法规继续进入审核。触发 schema 具有独立版本，并写入 KB 构建清单和报告。

## 7. Implementation Phases

### Phase 0：冻结试点真值与性能基线

**回溯**：US3、US5、US6。

1. 选择 10—20 条试点法规，覆盖保单贷款、等待期、宽限期、续保、费率可调、院外购药、身故责任、现金价值、重疾定义和固定禁止表述。
2. 每条由精算确认：触发事实、false 的证明标准、正确产品证据块、没有相关条款时的期望行为。
3. 至少使用 5 份产品，覆盖触发、明确不触发和未知。
4. 冻结 `trigger-truth-v1.xlsx/json`、文件指纹和 KB 版本。
5. 记录完整条款基线：法规数、调用数、Token、耗时和结论完整率。

**Gate**：没有精算真值的法规不得用于动态剔除验收。

### Phase 1：触发 schema 与 Excel 转换

**回溯**：US2、US5、US6。

涉及：`scripts/lib/common/compliance_audit.py`、实际 2026 Excel 转换入口、`scripts/lib/rag_engine/kb_rebuild.py` 和 metadata 测试。

1. 增加冻结触发模型和 schema 版本。
2. 转换 Excel 受控列并校验运算符、事实名、主题和证明策略。
3. 非法值阻止构建，不得静默忽略。
4. KB catalog 和法规条款单元保留触发规格。

**验收**：相同 Excel 稳定生成相同 metadata；非法配置不能进入 KB。

### Phase 2：一次性产品事实账本

**回溯**：US1、US5。

涉及：`scripts/lib/common/compliance_audit.py`、`scripts/lib/compliance/fact_extraction.py`、`scripts/lib/doc_parser/pd/clause_tagger.py`、`scripts/lib/compliance/audit_pipeline.py`。

1. 将事实提取从“每法规包重复执行”提升为“每产品一次”。
2. 汇总候选法规需要的 `fact_name` 并去重。
3. 依次复用产品名称标签、标题主题、正文词组和现有确定性事实。
4. `true / false / unknown` 均记录证据、方法、置信度和原因。
5. 不从“没有命中关键词”直接推出 false。
6. 冲突证据返回 unknown，并保留冲突条款。

**验收**：同一事实只提取一次；所有 true 有逐字证据；不安全负向推断均为 unknown。

### Phase 3：确定性触发求值器

**回溯**：US2、US5。

新增 `scripts/lib/compliance/regulation_triggers.py`，接入 `audit_pipeline.py`。

1. 用受控运算符求值，不执行任意表达式。
2. 满足期望值输出 triggered。
3. 第一版只有经验收的互斥分类或封闭词表全文扫描才能输出 not_triggered；开放世界功能的明确否定仍保守保留。
4. 缺失、低置信度或冲突事实输出 indeterminate。
5. indeterminate 保留法规；报告记录状态和理由。

**验收**：试点真值中 not_triggered 精确率 100%；unknown 不造成排除。

### Phase 4：安全动态条款证据检索

**回溯**：US3、US5。

涉及 `clause_routing.py`、`tokenizer.py`；仅在职责需要时新增 `scripts/lib/compliance/clause_evidence.py`，词组和阈值放在 `scripts/lib/compliance/data/`。

第一轮正文候选按证据强度组成：

1. 触发事实的证据条款；
2. 与 `target_topics` 精确匹配的条款；
3. 受控关联主题条款；
4. 满足业务对象词组约束的条款；
5. 达到最低 BM25/语义分数门槛的条款。

约束：

- 不再无条件 Top K；全部低于门槛时返回“未找到相关条款”。
- 父级只提供编号、标题和路径，不自动提交整个子树正文。
- “保单贷款”不能只凭“现金价值”命中。
- unknown 条款保留在完整目录，可供二次请求，但第一轮不全部提交正文。
- 结果记录选择原因、分数和来源。

前置适用性层只要检测到新版事实触发 metadata，就不得因旧产品标签冲突提前排除法规；候选必须留给 Phase 3 的事实求值器处理。

**验收**：试点法规正确条款召回率 100%；错误业务对象不得因单一共同词进入第一轮。

### Phase 5：未决事实的批量 GLM 提取

**回溯**：US4、US5、US6。

复用 `scripts/lib/llm/`，在事实提取和审核编排中实现：

1. 所有 unresolved fact 按产品去重。
2. 一次请求包含多个独立事实任务，结果与证据逐任务隔离。
3. 只发送相关候选条款，不发送全部法规。
4. 输出限于 true / false / unknown 和产品证据 ID。
5. 校验证据 ID、原文、任务完整性和冲突。
6. 无响应、漏答、低置信度或无证据保持 unknown。
7. 一份产品默认最多 1—2 个事实补充请求，不按法规扇出。

事实补充客户端在主链中保持显式注入、默认关闭。只有试点触发规格已由精算批准，且本次产品外发范围获得明确授权时，部署层才可注入现有审核模型客户端。

**验收**：GLM 失败不排除法规；并发不改变事实和证据归属。

### Phase 6：按需扩大上下文与最终 GLM 审核

**回溯**：US3、US4、US6。

涉及 `scripts/lib/compliance/auditor.py`、`audit_pipeline.py` 和公共审核模型。

1. 第一轮提交触发证据、检索正文和完整编号目录。
2. 模型只返回证据 ID，原文由程序解析。
3. `needs_more_context=true` 时不得形成确定结论。
4. 补充编号必须真实、一次最多 5 个，只允许一次扩展。
5. 禁止性固定表述使用经精算确认的封闭词表全文扫描；相关正文解析不完整时不能形成零命中符合。页眉、页脚和已确认二维码不属于审核正文，允许忽略；文本框与脚注/尾注必须纳入正式证据，批注只作审计留痕；只有仍可能承载产品条款文字的未解析图片或对象才撤销对应事实的覆盖证明。
6. 正向义务 compliant 必须有产品事实或条款证据。
7. 二次扩展仍不足则输出 insufficient_information，不无限追问。

**验收**：无虚构编号、自相矛盾状态或模型改写证据；确定结论全部通过程序校验。

### Phase 7：准确率、性能和降级验收

**回溯**：US3、US4、US6。

对比完整条款基线和动态链路：触发事实准确率、not_triggered 精确率、法规保留召回率、产品证据召回率、调用数、Token、耗时、限流和 incomplete 数量。相同输入并发重复运行时，结论、证据 ID 和失败状态必须一致。

**上线门槛**：

- not_triggered 精确率 100%；
- 核心法规保留召回率 100%；
- 核心法规证据条款召回率 100%；
- 无证据不合规结论为 0；
- 15 分钟内尽量完成全部法规，到期项如实标记 incomplete；
- 精算签署试点验收表。

### Phase 8：影子运行与生产切换

**回溯**：US4、US6。

1. 动态链路先与完整条款链路影子对照，不影响正式结果。
2. 差异按触发、检索、模型、系统失败分类。
3. Phase 7 全部通过后才切换默认路径。
4. 动态链路失败时回退完整条款并标记 degraded。
5. 稳定期后删除原型和临时兼容逻辑，不长期保留双轨死代码。

## 11. Complexity Tracking

| 项目 | 必要性 | 更简单方案及排除理由 |
|---|---|---|
| 三态事实账本 | 未命中不能普遍证明不存在 | 布尔值简单但会把 unknown 当 false |

## 12. 执行结果（2026-08-07）

- Phase 1—8 的工程能力已实现，动态条款证据保持影子模式，正式审核仍提交完整产品条款。
- 触发排除受全局模式、精算验收集、切换门禁、KB schema、Excel 源指纹、KB catalog 指纹、候选冻结和检索降级八项条件共同约束；任一条件不满足都不排除法规。
- 产品事实补充协议已实现并通过离线模型桩验证，但生产入口默认不注入客户端，不会新增产品条款外发。
- real-019 离线结果：60 个产品条款块、75 个法规单元；每单元影子证据正文均值 5.08 块，P95 为 6 块，估算上下文字符减少 59.7%。
- 当前 v5 的 75 个候选法规单元均未配置触发规格，因此全部保守保留；本轮只能验证工程链路，不能证明第二轮法规过滤收益。
- Phase 8 基线曾因 real-019 的文本框、二维码和页眉/页脚把解析完整性证明降为 false；Phase 9 按本节的新边界重新解析，旧结果只作为迁移前基线，不再代表当前语义。
- 生产切换仍需：在法规 Excel 中配置首批触发规格、精算签署真值验收集、重建 KB、通过门禁和影子对照。

## 12.1 Phase 9：解析覆盖精细化（2026-08-13）

用户确认页眉、页脚和二维码不属于产品条款审核范围，可以忽略。其余内容按“先提取、再证明、最后逐事实降级”处理：

1. DOCX 的实质文本框和被正文引用的脚注/尾注进入规范化正文；文本框的兼容性副本、可证明为目录导航的副本和二维码提示文字去重或忽略。
2. 批注属于审阅信息，保留作者、时间、锚点和原文以供追溯，但不得进入产品条款、标签或 LLM 审核上下文。
3. PDF/DOCX 图片先做本地确定性分类。二维码、页眉页脚图片、微小排版图元及已有文字层完整覆盖的装饰图不影响证明；无法排除承载正文文字的图片保持未解析，不调用云端 OCR。
4. 覆盖证明绑定到会使用“全文未命中”形成 false/none 的具体事实。一个事实的证据范围不完整，只让该事实保持 unknown，不连带撤销无关事实。
5. 全局 `coverage_attested` 继续服务于任意禁止性全文扫描；逐事实覆盖列表用于产品标签和法规触发事实。两者都由解析端签名，审核端不得信任客户端自报。

最终实测 23/23 份真实产品均通过正式正文覆盖证明；产品标签、风险事实和法规适用性相对已签收 v7 的变化均为 0。此前因把所有版面对象一律视为未解析而产生的 v8 复核需求已经消除，v7 签收继续有效。

```text
→ Phase 6 最终审核与按需扩展
→ Phase 7 验收
→ Phase 8 影子切换
```

Phase 0—4 可完全离线交付；Phase 5 后才需要在线 GLM。

## 13.1 任务级证据 ID 与费率组独立成对验证

模型不再复制逐字摘录，只能从当前法规任务的受控目录中选择证据 ID；服务端按任务、证据域和 ID 精确回填不可变法规正文或产品条款正文。法规、产品和产品名称使用互斥且带稳定任务前缀的命名空间，批量任务、漏答补问、紧凑修复及分段重排不得改变 ID。未知、重复、跨任务或跨证据域 ID 均失败，不再允许通过模型摘录反查并纠正错误 ID。

该简化只替换传输协议，不放宽结论门禁：不合规仍需法规与产品双证据；动态部分正文不能使用全文禁止性零命中豁免；`PNAME` 仅在法规主题明确允许产品名称证据时进入目录；正向义务、数值边界和复合要求不得以“全文未发现”判为符合。最终 API 模型继续输出程序回填的原始证据，保持可追溯性。

在线验证缩为同一产品、同一组三条费率可调法规的两阶段试验。先运行动态条款 C，只有三条法规都返回有效且证据能在各自审核包中精确复核的确定结论，才允许运行全文 A。C 与 A 是两个独立受控子进程，各自重新获得 25 万 token、10 次物理调用、285 秒内部 deadline 和 300 秒 watchdog；整组理论最大资源为 50 万 token、20 次调用和 10 分钟。A 启动前必须在任何供应商 I/O 之前验证 C 报告、证据协议版本、产品/KB/法规/model/官方端点及报告 SHA；C 失败时 A 调用数必须为 0。

## 13.2 单法规最小在线探针

三法规动态批次在45秒窗口内没有返回有效响应，因此下一轮只验证其中证据最完整、输入最小的第2条费率调整法规。该条法规与产品2.3“费率调整”条款能够直接对应首次调整间隔、后续调整间隔、分组调整及不得因个体健康或理赔差异调整费率等要求，适合作为任务级证据ID协议的最小在线探针。

单法规探针继续引用已批准的基础计划、real-001产品SHA、KB build及live catalog指纹、`glm-4-flash-250414`和智谱官方HTTPS端点。新的冻结overlay必须精确锁定一个法规单元，不得通过自定义文件、参数或直接调用runner扩大产品和法规范围；原三法规pair门禁保持不变。单条仍使用独立子进程watchdog并关闭上下文扩展、全文修复及供应商隐式重试。在线前必须先生成不外发的预检，确认只有一个法规单元、一个主请求、任务级法规/产品证据目录及调用前预算均符合冻结值。

本次新授权测试把资源进一步锁定为最多125,000 token、1次物理调用、285秒内部deadline、75秒HTTP上限和300秒watchdog。完整外发消息同时冻结内容指纹，任何产品名称、条款目录、法规正文、目标条款或证据目录漂移都会在供应商I/O前拒绝。有效结果必须是`compliant`或`non_compliant`、不完整和错误码均为空，并同时包含当前任务的法规与产品证据；程序回填原文必须与冻结审核包完全一致。超时、无响应、无效ID、证据不足或任何范围漂移均停止并转人工，不自动补问或重试其他法规。

## 13.3 法规义务逐项审核与并发边界

单法规证据ID探针虽得到正确总体结论，但总体理由没有覆盖法规的全部要求。法规审核包因此新增冻结的义务目录；模型必须按义务ID和目录顺序逐项返回状态、理由及当前任务内的法规/产品证据ID，程序再回填不可变原文并由逐项状态推导总体结论。漏项、增项、乱序、跨任务证据或总体状态与逐项结果不一致均失败关闭。模型额外返回的总体证据ID属于冗余信息，程序忽略并只从逐项证据重新汇总。

在线试验显示：两法规共13项义务合批时，GLM-4 Flash每条只回答第一项；改单法规后能够完整回答6/6项，单次耗时23.505秒。但模型对“分组方式与产品定价政策一致”作出了超出条款证据的满足判断，因此逐项结构完整不能代替证据语义充分性校验。历史在线实验使用的v1目录保持不变；安全修订后的v2目录把定价政策一致性、首要位置和字号/黑体等当前审核包不能证明的义务标记为不可自动判断，由程序固定输出`insufficient_information`。这一机制只覆盖已冻结试点目录，扩展到全部法规前仍需逐义务确认所需证据范围。

并发采用独立单法规调用而非多法规合批。实测并发2时2/2请求均返回，无429或超时；并发4时只有2/4成功，另外2路在约0.6秒收到智谱`429/1302`账户限流。当前账户的生产并发因此固定为2，不执行已确定会增加限流的并发6。法规候选数量不设上限，全部进入队列；整份审核总截止时间调整为15分钟，到期未完成或限流失败的法规统一标记`incomplete/manual_review`，不得当作合规。

## 14. Review Gates

1. 是否接受触发事实三态，并且只有经验收的互斥分类或完整封闭扫描才能形成可排除 false；
2. 法规 Excel 是否作为触发条件的精算维护源；
3. 第一批是否只做 10—20 条代表法规，而非一次覆盖全部；
4. 未配置触发条件的法规是否继续全部进入审核；
5. unresolved 事实是否最多合并为 1—2 次 GLM 提取；
6. 动态证据未达到 100% 核心召回前，生产是否继续完整条款模式；
7. 完整解析证明成立时，固定禁止表述是否采用封闭词表全文扫描；
8. 是否继续使用云端 GLM-4 形成最终法规结论；
9. 是否采用端到端15分钟、不限制法规候选数量、当前智谱账户最大并发2；到期未完成的法规明确标记`incomplete/manual_review`。
