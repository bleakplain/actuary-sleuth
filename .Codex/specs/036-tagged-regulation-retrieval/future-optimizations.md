# 审核架构后续优化提醒

本文记录本次重构明确暂缓、但需要在新主链稳定后重新评估的事项。

## OPT-001：将高可靠事实检查升级为确定性结论

**本次决定**：第一版采用方案C。确定性程序只提取事实和机械比较结果，最终法规结论由同一条LLM主链生成。

**为什么暂缓**：

- 当前规则中仍有适用范围、触发条件、单位和法规例外建模不足；
- 现有单测主要证明正则行为，不足以证明真实产品上的监管准确性；
- 直接启用硬结论会重新引入双轨冲突风险。

**重新评估时点**：

1. 新主链完成Phase 7并通过真实产品精算验收；
2. 已积累足够的人工标注结果，可以逐规则计算精确率和召回率；
3. 可以证明某条规则不存在未建模的产品适用性、业务触发条件或法规例外。

**届时需要用户确认**：

- 哪些事实规则允许绕过LLM直接形成结论；
- 每条规则需要达到的准确率和样本量门槛；
- 硬结论与LLM意见冲突时采用什么优先级；
- 是否继续要求抽样人工复核。

## OPT-002：法规条款单元的小批量LLM请求

**本次决定**：暂不实现物理请求批处理。第一版一个法规条款单元对应一个 HTTP 请求，最多并发 5 个。当前供应商接口只接受一个 messages 会话，把多个单元拼进同一 prompt 会变成逻辑合并判断，无法保证独立错误和证据归属。

**需要持续观察**：

- 小批量是否造成法规之间相互污染；
- 单批法规数量对准确率、延迟和token成本的影响；
- 429、超时和重试率；
- 单元证据是否始终严格隔离。

**重新评估时点**：

- Phase 5性能基准完成时；
- 端到端5分钟目标无法达到时；
- 模型或供应商发生变化时。
- 供应商提供原生多任务 batch API，且能为每个任务返回独立身份、错误和结果时。

## OPT-003：扩展直接确定性条款主题识别

**当前状态**：受控注册表已有59个主题，其中27个主题配置了共47个确定性关键词；续保额外支持
`renewal.guaranteed`、`renewal.non_guaranteed` 两个正文派生子主题。

以 2026-07-28 编号解析器 v2 对
`/Users/plain/work/actuary-assets/products` 中23份主目录产品的扫描为基线：

- 1,569个条款块中456个有主题，覆盖率29.1%；
- 1,113个条款块无主题，占70.9%；
- 440,149个条款字符中106,918个属于有主题块，占24.3%；无主题内容占75.7%。

这不会直接造成漏检，因为 unknown 条款默认保留，但会扩大法规审核包、增加LLM成本和噪声。本项属于新主链稳定后需要优先处理的优化。

**后续方向**：

- 补充既往症定义、诉讼时效、生存保险金、死亡责任、重疾比例等审核所需主题；
- 对标题不规范但正文信号明确的条款增加可解释识别；
- 对重疾/疾病定义等大量唯一但未编号内容建立稳定结构和主题，避免它们以 `unclassified` 身份进入每个法规包；
- 每次新增主题同步更新关系配置和fixture；
- 无法确定时继续保持unknown，不用强行分类换取覆盖率。

**验收口径**：

- 同时报告按条款块和按字符量的覆盖率；
- 在精算标注集上衡量主题准确率与核心主题召回率，不以覆盖率单独作为成功标准；
- 优先保证核心监管主题召回，错误标签不得导致条款被判为“明确不相关”；
- 优化前后使用同一组去重产品样本对比，并单独报告 unknown 比例；
- 目标值待完成人工主题标注后确定，不能为了达到固定百分比强制分类。

## OPT-004：可取消的 LLM 调用与容量保护

**当前实现**：

- 整份审核预算为300秒，最大并发5；
- 同一 API 进程内所有审核请求共享5个模型调用配额，不再按请求各自放大；
- 单次 HTTP 超时不超过45秒，并受法规单元剩余 deadline 约束；
- 已关闭 HTTPAdapter 内层重试，只保留能检查 deadline 的外层重试；
- 到达总 deadline 后，未完成法规单元立即标记 `incomplete`，不会形成整份产品合规结论。

**仍然存在的限制**：

Python 线程和 `requests` 无法强制终止已经开始的 HTTP 请求。审核计算能在预算内形成不完整结果，但超时瞬间仍在运行的少数请求会继续到自身 HTTP 超时后才释放。进程级配额可以限制单 worker 放大，多个 API worker 之间仍没有共享队列；若供应商持续卡住，可能短时积累后台调用、连接和费用。

**后续方向**：

- 优先采用供应商支持取消的异步客户端；
- 为整份审核增加进程级隔离或可回收 worker；
- 将当前进程级上限升级为跨 worker 共享配额、用户级排队和熔断指标；
- 压测连续超时场景，观察活动线程、连接数和实际计费。

## OPT-005：禁止性法规的“缺失证明”

第一版要求 `compliant` 同时引用法规证据和产品原文证据。对于“条款不得包含某表述”这类通过全文未出现才能满足的法规，目前不会因为没有可引用产品片段而输出绿色结论，而是进入 `insufficient_information` 或人工复核。

后续如需自动确认此类合规，需要建立可验证的覆盖证明，例如：

- 记录参与检查的完整条款块集合及文档指纹；
- 记录禁止模式、扫描范围和扫描器版本；
- 让 LLM 只能引用该覆盖证明，而不是把“没看到”当作事实；
- 在精算验收集上验证遗漏率后，才允许形成 `compliant`。

## OPT-006：v6 知识库身份迁移

候选冻结现已绑定 `kb_build_identity.json` 中的版本、构建清单 SHA-256、文档/chunk 数和稳定目录内容指纹。发布 v6 时必须显式生成并复核新的受控身份；未更新身份配置时，系统会把候选冻结标记为 `incomplete`。

迁移时还需要：

- 以新版本重新运行法规适用性和条款路由，不复用 v5 的 `not_applicable`；
- 保留历史报告的 v5 法规单元和 chunk ID；
- 同步版本化主题体系、主题关系和验收集；
- 在切换默认入口前重新通过精算验收门。

## OPT-007：多进程解析凭证的共享密钥治理

解析凭证使用 HMAC 绑定解析身份、文档指纹、产品名称来源、警告摘要和用户身份。认证启用时，服务现已在启动阶段强制要求非空 `AUTH_JWT_SECRET`，JWT 与解析凭证共同使用其派生密钥；缺失时 fail closed。`AUTH_SKIP` 开发模式使用固定的仅开发密钥，因此同机多 worker 不再随机 409。

生产切换前仍需：

- 由部署平台向所有 API worker 注入同一个高强度 `AUTH_JWT_SECRET`；
- 在多 worker 环境增加“解析后由另一 worker 审核”的集成测试；
- 设计密钥轮换期间的短时双密钥验证窗口，避免正在进行的解析凭证全部失效。

## OPT-008：报告列表分页与轻量摘要

报告现已保存 `owner_user_id`：普通用户只能访问自己的报告，管理员可以治理全部报告；迁移前没有 owner 的历史报告只对管理员可见。

当前列表接口仍会一次读取并反序列化完整 `result_json`。候选报告包含法规正文、路由和产品证据，报告量增加后会放大数据库内存、网络传输和前端解析成本。默认入口切换前应：

- 为列表接口增加稳定游标分页；
- 列表只返回 ID、产品名、状态、摘要计数、版本和创建时间；
- 完整法规正文与证据仅在详情接口按 ID 读取；
- 为管理员全局列表和普通用户列表分别做容量与权限回归。

## OPT-009：产品文档深层资源边界

解析入口现已限制上传文件为25 MB、富文本为500万字符，并将 DOC/DOCX/PDF 转换和解析移出 async 事件循环。

后续还需要针对压缩炸弹和结构复杂度建立解析器内层预算：

- PDF 最大页数、DOCX 解压后总大小和 XML 节点数；
- 最大审核块、表格行列和单块字符数；
- 旧 DOC/LibreOffice 转换使用隔离 worker、CPU/内存配额和可回收进程；
- 超限时返回结构化、可审计的解析失败，不生成不完整审核输入。

## OPT-010：跨维度复杂适用条件的受控分支

**本次决定**：第一版只实现“主体范围 OR 风险触发”的保守旁路。法规存在跨维度复合条件、例外或多组 OR 分支，而现有标签结构不能无歧义表达时，扩大候选范围，不把复杂条件压缩成会漏检的硬过滤。

**当前代价**：部分产品会多检查法规，增加检索、路由和 LLM 成本；但不会因错误建模把异常产品设计提前排除。

**后续方向**：

- 引入版本化的受控适用分支，例如 `any_of` 下的多组 `all_of` 条件；
- 每个分支分别记录主体事实、风险触发和未知值，禁止自由文本直接控制排除；
- 用精算验收 fixture 覆盖每个分支的正例、明确反例和 unknown；
- 新结构只能在证明不降低核心法规召回率后启用。

## OPT-011：检查目标标签受控化

**本次决定**：`检查目标标签` 只用于向审核模型说明“需要核验什么”，不参与法规排除。当前先保留法规源中的可读文本，避免因不成熟的代码表影响召回。

**后续方向**：

- 建立版本化检查目标代码表，并保留中文释义；
- 将自由文本映射为受控代码时记录未识别 warning，不静默丢弃；
- 与条款主题、事实提取器和 LLM 输出字段建立一对多映射；
- 配置变更必须经过法规原文抽样和精算验收，不得因目标标签缺失排除法规。

## OPT-012：法规标签词表单一来源与构建门禁

风险触发代码当前由 Excel 转换器负责中文映射、适用性模块负责运行时识别。两处已经有一致性测试，正式 v5 也没有把风险触发误写进硬适用标签，但双份词表长期存在漂移可能。

后续应把主体标签、风险触发和检查目标代码集中到一个版本化数据文件，并在构建时强制验证：

- 风险触发不得通过“特殊属性”等旧列混入硬适用标签；
- 转换器产生的每个代码都必须被运行时识别；
- 未知代码只能产生 warning 和保守保留，不得静默排除；
- 词表版本写入 KB manifest 和审核报告。
