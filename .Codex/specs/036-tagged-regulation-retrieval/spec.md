# Feature Specification: 产品标签驱动的产品条款审核主链

**Feature Branch**: `036-tagged-regulation-retrieval`
**Created**: 2026-07-28
**Status**: Approved
**Input**: 将产品条款解析、产品标签、法规适用性、条款主题路由、事实提取和法规级 LLM 判断统一为一条可追溯审核主链。

## User Stories

### US1：生成唯一、可追溯的产品审核输入（P1）

用户上传 DOC、DOCX 或 PDF 产品条款后，系统识别正式产品名称，按文档结构提取条款块，为可确认的条款赋予受控主题，并只生成一份带证据的产品标签。

**独立验收**：

- DOC、DOCX、PDF 可解析为稳定条款块；
- 每个条款块具有稳定 ID、标题、原文和零个或多个受控主题；
- 无法识别主题的条款保持 unknown，原文不丢失；
- 用户填写名称、正文名称和文件名按明确优先级取值。

### US2：只排除明确不适用的法规（P1）

系统使用产品标签与法规限定标签执行三态匹配，只排除存在明确维度冲突的法规。

**独立验收**：

- 同维度法规多值按 OR，不同维度按 AND；
- 产品标签 unknown 产生 indeterminate，不产生排除；
- 每个保留或排除结果都有原因和证据；
- 法规候选身份包含知识库版本和稳定法规条款单元 ID。

### US3：为每条法规安全路由产品条款（P1）

系统以受控主题和显式关系为每个法规条款单元选择直接相关、可能相关、未知和明确不相关的产品条款。

**独立验收**：

- 精确主题和必要跨主题条款优先；
- unknown 条款默认保留；
- 只有经过版本治理并有 fixture 覆盖的明确无关关系才能排除；
- 每个未提交给模型的条款块都有受控排除理由。

### US4：逐法规形成有证据的 LLM 结论（P1）

LLM 针对一个独立法规条款单元及其候选产品条款输出结构化结论，且不能改变前置适用性。

**独立验收**：

- 输出限于 compliant、non_compliant、insufficient_information、manual_review；
- non_compliant 必须同时引用法规证据和产品条款证据；
- 无效输出、调用失败或证据不足不得变成合规；
- 第一版一法规条款单元一 HTTP 请求，最多并发 5 个，各单元的 prompt、输出和证据严格隔离。

### US5：确定性程序只提供事实证据（P2）

系统从法规审核需求出发提取天数、比例、续保安排和固定表述等事实，不迁移旧 Python 规则中的监管语义。

**独立验收**：

- 事实输出包含值、单位、来源条款 ID、原文和置信度；
- 提取失败返回 unknown；
- 事实提取不直接输出合规或违规；
- 旧规则结果不合并进新主链。

### US6：降级、版本和审核覆盖可见（P1）

用户能区分无违规、信息不足、人工复核、系统降级和审核未完成。

**独立验收**：

- 报告记录 KB、主题体系、主题关系和精算验收集版本；
- 报告记录候选数、排除数、失败数和未审核范围；
- 任一关键失败不会显示为“0 条违规即合规”；
- 历史报告保留原版本证据。

## Functional Requirements

- **FR-001**：系统 MUST 使用一份 `ProductTags` 作为产品适用性事实来源。
- **FR-002**：系统 MUST 保留所有解析出的原始条款块；主题未知不得造成删除。
- **FR-003**：系统 MUST 使用 applicable、not_applicable、indeterminate 三态法规匹配。
- **FR-004**：系统 MUST 只在明确标签冲突时排除法规。
- **FR-005**：系统 MUST 用 `kb_version + source_file + article_number/section_path` 标识法规条款单元。
- **FR-006**：系统 MUST 使用版本化的受控主题表和关系表。
- **FR-007**：系统 MUST 对每个法规条款单元形成独立审核包。
- **FR-008**：LLM MUST 只引用审核包中提供的法规和产品条款证据。
- **FR-009**：系统 MUST 拒绝无产品条款证据的 non_compliant 结论。
- **FR-010**：单元失败 MUST 标记 manual_review 和 incomplete，并继续其他独立单元。
- **FR-011**：事实提取器 MUST 不形成最终合规结论。
- **FR-012**：旧 `rule_engine.py` 结果 MUST 不进入新主链，并在切换完成后删除旧生产路径。
- **FR-013**：并发 MUST 不改变结论集合或证据归属；没有原生 batch API 时 MUST NOT 把多个单元拼进同一 prompt。
- **FR-014**：端到端审核目标时长暂定不超过 5 分钟，初始最大并发为 5。
- **FR-015**：法规正文要求或禁止的产品属性 MUST NOT 作为证明产品已经合规的前置排除条件。
- **FR-016**：受控风险事实命中时 MUST 保留法规候选，即使产品分类标签与法规常规主体标签冲突。
- **FR-017**：复杂条件、异常产品设计或受控风险事实未知时 MUST 保守保留；额外检查成本优先于漏法规风险。
- **FR-018**：特定疾病专项身份、是否涉及“院外购药”或“药店”表述和恶性肿瘤专项身份 MUST 作为有证据的三态产品事实，不得由上位险种标签直接替代；院外购药标签只表示条款是否涉及相关表述，不表示产品一定承担该责任。

## Success Criteria

- **SC-001**：精算验收集中的核心适用法规召回率为 100%。
- **SC-002**：明确不适用法规排除准确率为 100%。
- **SC-003**：核心法规所需产品条款块召回率为 100%。
- **SC-004**：所有 non_compliant 结论均可追溯到法规和产品条款原文。
- **SC-005**：系统失败、信息不足和无违规三种状态不会混淆。
- **SC-006**：相同输入并发重复执行时，结论集合与证据 ID 集合严格一致。

## Assumptions

- 当前只审核产品条款，不覆盖产品说明书、精算报告或销售材料。
- v5 法规原文及已验收元数据是本次实现的唯一监管依据。
- unknown 的错误保留成本低于错误排除导致的漏检成本。
- 法规主体范围、风险触发事实和待审核的合规要求是不同语义；只有主体范围和必要触发事实可参与候选过滤。
- 条款主题覆盖率优化属于后续工作；当前 unknown 条款全部保守保留。
- Phase 0 的具体精算样例仍需在执行中形成版本化冻结清单。
