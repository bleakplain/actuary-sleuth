## 执行补充（用户后续指示优先）

用户要求“执行，模型方面你就用自己做对比试试”。第一批将当前会话助手作为开发集参考作答方，与项目现有模型的同证据结果对照，不先引入另一个候选模型。记录问题、实际提供的证据、参考答案和证据指纹；助手已知历史失败例子，不能称盲测或专家金标，也没有独立 API 延迟、费用与多次运行稳定性成绩。本会话不是项目可直接调用的模型接口，不读取/转用 Codex 登录令牌、不将会话订阅默认为项目 API 授权。正式模型切换、付费和发布仍须分别确认。

Phase 0 先完成这组开发诊断和确定性合同测试，人工金标与可复现 API 对照未完成时明确保留为待验收。继续实施不依赖该结论的检索、预算、状态与协议修复，不用参考答案对照替代正式质量门槛。原模型候选与实验预算表保留为可选后续方案，未启用的模型调用不执行。

## 1. Summary：换主路线，不继续叠加逐题补丁

目标是“问得自然、解释清楚、依据可查、等待合理”，而不是把每次聊天变成正式合规审核。采用现有检索能力上的短路径问答：**先验证模型能读懂正确资料，再解决资料覆盖，最后精简核对与交付链路**。不是关闭校验，也不以“供参考”放行已知错误。

首期继续使用独立 QA 大库、本机 embedding/BGE、现有供应商与前后端。不先建全书本体、不换图数据库、不迁移整套框架。当前模型与官方列为免费的同供应商候选先做对照；若资料给全仍答不稳，停止用大量规则为其补救，提出模型/成本取舍再决定。

ima 公开资料可支持把自然提问、资料解读、来源追溯作为产品参照，不能证明其内部架构或本库准确率。没有获准用相同资料做盲测前，以本项目试用门槛为目标，达标后才试用，不宣称“等同 ima”。依据与模型价目见 [research.md](research.md)。

## 4. 目标执行路径与预算

```text
用户问题＋必要历史
  → 独立问题直接检索；有指代先至多一次理解与规划
  → 独立概览可用原问种子检索的标题做一次规划（计入同一首轮）
  → 原问＋有限子查询 → 混合检索/重排 → 结构闭包与覆盖检查
  → 统一生成一次 → 快速确定性核对 → 必要时批量语义核对
  → 有具体缺口时一次补检索/修订 → 交付完整或诚实的部分解读
```

“一次补检索”是全请求共享额度，覆盖检查已使用后修订阶段不得再开一轮。模型规划、别名/本体扩展与修订不能各自展开无限查询。预算是初始实验参数，不是新增一套复杂可配置工作流；集中在现有 constants 并记录实际消耗。

- 检索最多 6 条去重后的查询字符串（含原问、别名、子问题）；首轮最多 4 条，剩余最多 2 条用于一次缺口补充，简单问题不必填满。原问必留，显式子问题/缺失维度优先于别名。每条可走 BM25 与向量两路，最多 12 个通道任务；按 `(query, channel)` 去重/记录实际执行，不能在下层再次展开。所有子查询继承权限、库、时点及版本约束，不由模型重新决定。
- 常规问答通常 1 次生成，必要时增加核对；内容调用最多 3 次，额外理解/规划至多 1 次，全请求最多 4 次。独立问题及可确定性形成的维度不用模型规划。预算包括所有外部 LLM 路径、失败请求及将来可能启用的 LLM 重排，不用传输重试绕过；沿用请求内单次尝试策略。
- 三次是上限，不是固定顺序：已确认错误优先“生成 → 补证据/修订 → 语义终检”；软疑点优先“生成 → 语义核对”。每步同时看剩余时间、证据是否可补和结果是否可验收。若已用两次且第三次修订预计仍需语义终检，不做注定无法验收的修订，只交付独立已支持内容；第三次可用于能确定性验收的引用格式修正等。不能把未完成核对改成通过。预算若导致系统性误拒，先调整核对顺序/模型，不降低安全门槛。
- 初检和修订共用上下文装配：先保留已支持内容的依据及必要条件，再填缺口；维持当前 12000 字证据总上限做初始对照，按实际渲染后的证据正文与来源标签计算，同时检查完整请求的模型 token 上限与输出预留。修订不能在原预算外简单追加 4000 字。预算不足时整组舍弃并标记缺口，不能截断表注/条件；来源编号不因删选重排。
- 不做每个子问题各生成一份答案，不默认开启代理循环，不把“核对未完成”改名为“已验证”。

## 5. Implementation Phases

### Phase 0：先验证瓶颈，确定模型路线（0.5–1 工程日）

**回溯：US1、US3、US4；依赖：无。** 先跑诊断再投入主要重构；离线结构/测试工作不因付费未获批而暂停。

1. 冻结实际代码、库 manifest、prompt、模型参数及现有失败报告。沿用 `scripts/evaluate_rag.py` 与 `evaluator.py:35,56,164,238`，在现有评估结构补充“人工确认记录”，不把只允许 `pending` 的现有 loader 绕过去。机器预标文件保留；确认人、时间、证据定位及判断存入独立标签记录，调参与封存按问题族隔离。修正 `evaluate_rag.py:263` 将无 split 题混入目标集的行为：正式模式要求 family/split 完备且精确匹配。由独立维护者导出仅开发题的输入文件，开发者不通过先加载全量再过滤的方式接触封存；两个集合及人工标签均有独立哈希。
2. 先让人员确认开发集 15 题的必要证据与禁错点：10 个可回答、5 个错误前提/资料不足等边界题。不要求撰写完整标准答案，不接触封存题正文。
3. 固定正确完整证据、同一问题与输出预算，对比当前 `glm-4-flash` 与 `glm-4.7-flash` 关闭思考。后者当前官方输入/输出免费，账户可用性、别名路由与速率限制待执行核验；不预判它更准。现 `zhipu.py` 已有 4.7 关闭思考适配，先测试透传，避免重复实现。价格依据：[官方价目](https://docs.bigmodel.cn/cn/guide/start/pricing)，参数依据：[思考模式](https://docs.bigmodel.cn/cn/guide/capabilities/thinking-mode)。
4. 首轮最多 `15题 × 3次 × 2模型 = 90次` 固定证据生成；随机交错顺序，记录实际返回模型 ID（若有）、终止原因、正文、token、延迟和失败。固定证据必须含真实条件、表头和例外；另选 12 组已确认的正确/错误主张测试核对能力，每模型一次共 24 次，分别报告误拦与错放，不拿模型自评生成稿当金标。旧别名不可用就如实记不可用，不静默换成另一模型冒充基线。选定候选再以实际检索证据做 15 题单次生成对照，不跑修订循环，区分“模型读不懂”和“检索没给全”；这一诊断不代替端到端验收。
5. 开发门槛：10 个可回答题中至少 9 题在三次运行均无关键错误且关键点完整；5 个边界题均不虚构关键法规事实，并按预定策略纠正/澄清/说明缺证据。两模型都失败时最多再做一轮有具体假设的诊断；仍不达标则停止模型周围的大范围补丁，报告具体差距和可选付费/成熟后端 POC，不消费未批准预算。

**产物/验收**：同证据盲化对照表、失败归因、选定或暂缓模型的结论。不开启封存集，不把 90 次重复当 90 个独立样本。模型调用只发生在后续获准的执行阶段。

### Phase 1：让宽泛问题找全必要资料（1.5–2.5 工程日）

**回溯：US1、US3、US4；依赖：Phase 0 的诊断，离线合同测试可并行。**

1. 修改 `rag_engine.py:868,918`、`query_preprocessor.py`：普通问题维持短路径；独立概览先用原问做种子检索，再依据问题与种子标题形成至多 3 个维度，规划至多调用模型一次，种子与后续维度检索共同消耗首轮 4 条额度。存在指代的多轮则先将理解和初步规划合为一次调用，后续章节反馈只作确定性补充，不再调用第二次规划。模型只能提出检索意图，不能把它猜测的规则当证据或“完整性证明”。保留原问、否定、日期、产品条件；子查询由原问首检+显式维度共同校正，不为补齐额度而扩展。
2. 修改 `retrieval.py` 与 `rag_engine.py`：各维度并行混合召回，统一重排；先满足相关性与高分锚点，再考虑文档多样性。不可为凑多样性挤掉强相关条文。用原问高相关候选和章节结构检查维度遗漏；找不到的维度标缺口，不虚构适用规则。
3. 修改 `rag_engine.py:964,1057`：将不可拆的表头/表注/列举与必要祖先组为结构单元；独立兄弟共享父节点不自动合并成整章。区分“已证实的前提/例外依赖”和“帮助理解的背景”。父链接只表示结构，不自动证明法律适用关系；未知关系不冒充已知。
4. 首检、`search_candidates()`、`repair.py` 修订取证及摘引交付共用同一个装配方法。真实的缺失依赖被权限/时点过滤时，相应主规则不可裸用；没有组元数据也不能视为已证明完整。保持全部证据的原始身份、版本和引用编号。
5. 覆盖指标测在最终 prompt 上：所需维度有无、证据条件是否完整、因预算舍弃什么。词项命中仍是定位辅助，不自动升级为语义覆盖。新增 `test_qa_evidence_groups.py` 的实际 `search_candidates → repair` 合同测试，避免手工 fixtures 掩盖链路缺口。

1. `graph.py:463` 只负责会话状态/路由，直接问答与 graph 统一复用现有 `rag_engine.py`、`repair.py` 的回答核心，不复制 prompt、预算和最终交付逻辑。删前先查调用点，不移除还被其他入口使用的 feature flag。
2. 精简重复来源管理字段及多次重复指令；来源身份保留在 metadata/引用卡片，生成上下文保留必要条款名称、时点、范围与正文。优先输出“直接结论—分情况解释—必要例外—引用”，不默认生成冗长审计报告；不能压缩掉决定结论的条件。
3. `attribution.py:1680,1935` 与 `repair.py` 改成下表分层。尤其修复“无关未引背景存在就整答待审”，但**无结构冲突不等于语义支持成立**；来源真实、主张相关与材料实际支持仍是基本要求。未知背景关系不等于已证明无关；明确例外、前提或高风险关系未确认时，仍须核对或缩小交付范围。

| 类型 | 在线处理 | 不允许的简化 |
| --- | --- | --- |
| 引用不存在/越权/版本错；明确数字、单位、上下限、主体、否定、例外冲突 | 阻断相关主张，最多一次针对性修订 | 一律放行后加免责话术 |
| 跨条归纳、非逐字释义的实质支持缺口、条件继承不明、权利义务/适用范围扩张 | 对相关主张批量语义核对，超时保持未完成 | “没有数字所以低风险”；让无关引用被其他材料洗白 |
| 逐字摘引且条件完整、确定性映射已证实的直接事实 | 快速确定性核对 | 把本体关系当法规效力或完整性证明 |
| 与当前主张无关的同章背景、风格/冗长评分、纯词面弱提示 | 记录诊断，不单独阻断；抽样离线分析 | 把真正缺乏支持的问题降成风格项 |

4. 修订只接受具体差错与证据缺口，已独立支持的结论和引用锁定；必要补检索先于修订，修订后对新增/改动主张重新执行相应检查。初稿事实错误不能直接展示。完整解释、部分解释、原文参考分开：原文摘引不是“修好后的完整答案”。
5. 通过现有 trace 保存初稿、修订稿、最终稿差异和每项结果/简短原因，补上目前只有修订长度的问题。不采集私有思维链，不记录密钥；仅在受限诊断记录中保存所需原文，设保留期限。当前普通 `ask` 权限可读取 trace、客户端可请求 debug，因此先补后端权限及出站脱敏，前端隐藏不是访问控制；普通用户的 trace 不返回新增全文诊断，测试越权路径后才启用记录。
6. `qa_budget.py`、API、检索与重排从请求接收起使用同一单调时钟预算，覆盖排队、首检、重排、生成、核对、保存，并为确定性终检与提交预留时间；预算到期不启动下一次调用。取消状态绑定 request ID，传递到可取消 I/O、关闭连接；发布、持久化和提交会话上下文前检查取消状态。用现有保存层实现取消/完成终态的互斥提交：取消先获确认则迟到结果只留诊断、不推进对话；完成已提交再收到取消则如实返回已完成，不删除已保存答案。限制 worker 总数和待排队数；无法中止的本机计算保留运行时租约与并发占用直到结束，不假称已杀线程、不提前放锁让同会话并行写历史。首期未能中断的计算仍属软截止，记录实际超限，不保证后台严格在某秒停止；用户等待结束与后台结束分别计时。

**验收**：既有真实正确答案不因无关背景被误拒；等待期固定天数、比例下限写成固定值、错引、未成年人例外、无数字的范围扩张仍被识别。每请求至多一次修订、预算无旁路；不同入口交付一致。高风险内容核对未完成不标“已验证”。

### Phase 3：对话层只展示用户需要的信息（0.5–1 工程日）

**回溯：US2、US4；依赖：Phase 2 的统一交付合同。**

1. 调整 `MessageBubble.tsx:101`，复用现有状态而非另造一套：默认简短结论与分类解释、就近引用、可展开原文；效力未知保持可见但不反复打断正文。对资料充分的宽泛问题先给概览，必要时结尾再问一个有用的条件。
2. `ask.py` 和 `askStore.ts` 区分检索中、生成中、确有发生的补充核对；不要固定动画冒充进度。技术超时说明为技术问题，资料不足说明缺什么；修订成功无需暴露内部失败过程。同步 API schema、SSE 类型与历史接口，补 `failure_kind` 的保存/序列化合同，刷新后不能把超时变成“法规库无依据”。
3. 首批仍允许完成核对后一次交付正文，重点是减少总等待，不用逐字动画伪装速度。若提前显示检索来源，明确是“找到的相关资料”，不是已支持答案的引用；交付时正文、引用和判断原子更新。
4. 保留现有 request sequence 防串会话机制；新增取消后迟到响应、主题切换、历史版本追问、重连与保存失败的端到端测试。以最终交付记录为准，不持久化未核清草稿；响应成功/保存失败应可识别与恢复，不能静默声称已保存。

**验收**：真实首进度 P95≤1 秒；正文状态与历史一致；取消后不追加正文到新问题；有据的答案不显示“回答有问题”模板。首反馈不计正文延迟。

#### 可选第二批：安全分段交付（额外 1–2 工程日，非首批前提）

只有完整答案质量通过且流式有可测收益时才实施。修改 `base.py:105`、`zhipu.py:327` 的流式预算、终止原因、取消与 usage 合同；目前直接把 `chat` 换成 `stream_chat` 不可用。

前后端增加稳定段落 ID 与序号，事件携带文本、引用及检查状态，避免 append-only 导致重复/错引。仅可交付证据和适用条件已闭合、后文不会反转的独立段落；若后续例外可能改变结论，等待整组/全文，不提前放出数字。断流保存已交付段落及未完成状态，重放幂等。首个可用段落延迟与完整正文延迟分别报告；不能用免责句冒充首段收益。

## 6. Phase 4：小规模真实验收，再决定替换（1–1.5 工程日）

**回溯：US1–US4；依赖：Phase 0–3。** 工程预计合计约 6–9 日（含集成余量），不是承诺日历期限，不含等待人员复核、限流恢复或重备封存集；首日模型试验后更新估时。可选分段另外计算。

### 验收集合与指标

- 重用 30 个问题族：15 调参、15 封存；每组 10 可回答＋5 边界，由人员确认最终分组。所有口语变体和追问跟随原问题族，不能将同题换词分到封存制造虚高成绩。
- 人员不必写长答案：确认“资料位置、应回答的关键点、不能犯的错误、是否应追问”即可。每组预计 45–90 分钟，合计 1.5–3 小时；模型对照及最终结果复核另留 2–4 小时，由领域复核者对照关键点勾选，工具先聚合同题重复结果及差异，不要求重复阅读完全相同文本。模型自评不能替代这部分判断；分歧多时更新估算，不将未复核项默认为通过。封存由独立复核者/执行阶段维护，不在开发时打开。
- 冻结代码/模型/库/prompt 后只做一轮封存验收，该轮预先规定每题 3 次，不按结果临时增加重跑。主指标按问题族聚合：原问及预定追问的关键点在 3 次均正确且完整才算一题通过；任何关键错答单列失败。边界题 3 次均须符合预定策略。额外口语变体另报鲁棒性，不加入独立题数凑分母。失败如用于修复，该集就不再是未见数据，须另补封存问题，保留失败报告。
- “系统性误拒”定义为人工已确认可答的场景中，有据且正确的答案被流程拦截/误称无依据，或无必要地要求补条件而不答；按出现过该现象的问题族计数，单次失败也不能藏在平均值中。模型本身生成错误、技术失败另记，二者仍使该题不通过完整解读。样本规模只支持限定试用，不支持整体 95% 准确率。

| 目标 | 放行标准（待测） | 测试与统计要求 |
| --- | --- | --- |
| 完整解读 | 20 个确认可回答锚定题至少 18 个关键点正确且完整，封存至少 9/10 | 不把原文/部分解读算完整；人工关键点为准，模型自评仅辅助 |
| 边界处理 | 每组 5 题均不编造关键法规事实，按预定纠正/澄清/缺证策略交付 | 技术超时不是正确拒答；纠正错误前提也可为完整回答 |
| 减少误拒 | 20 个可回答题系统性误拒≤1；已知 3 类失败探针各重复 3 次合理交付 | 重复探针不是独立准确率样本；同时记录事实错误与错误放行 |
| 安全底线 | 指定数字/范围/义务/例外、跨库、权限、时点与引用反例无已发现关键错误放行 | 不把样本零错误解释成总体无风险；越权和跨库为零容忍 |
| 完整正文时延 | 普通 P50≤8 秒、P95≤15 秒；复杂 P95≤25 秒 | 受控机器、相同并发与冷热状态；报成功样本数及全部请求终止时延/失败率 |
| 可感知响应 | 真实首进度 P95≤1 秒 | 完整正文/可用段落另计；不拿网络 token 到达或打字动画充数 |
| 调用效率 | 常规首答无需修订比例目标≥80%，修订比例目标≤20% | 分母为全部确认可回答请求，超时/失败保留；这是诊断目标，不得以放过错答达成 |
| 成本 | 每题所有调用、输入/输出/缓存 token、失败和总费用可追踪 | 免费模型不等于工程免费；缺 usage 明确标未知，不填零 |

正式时延另做固定 100 次受控开发集请求，独立问题/复杂问题各 50 次；不重复调用封存集调延迟。首次冷启动与稳定热态分开，并做至少两会话的隔离/取消压力回放；不在同时跑全量测试时宣布性能收益。若样本/配额不足，如实标探索结果，不以少量成功样本宣布 P95 达标。

### 整体实验上限

以下是停止上限，不是必须消费的额度；先过质量门槛再跑性能，失败调用也计入。单元/协议测试用 fixtures，不额外调用外部模型。

| 批次 | 请求/调用上限 | 备注 |
| --- | --- | --- |
| Phase 0 模型诊断 | 2 轮 × (90 生成＋24 核对)＋15 实际证据生成＝243 次模型调用 | 第二轮需有具体待验证假设；不是无限调参 |
| Phase 1–3 开发真实回放 | 60 请求，最多 240 次模型调用 | 含多轮、取消与集成检查，单个追问也算请求 |
| Phase 4 冻结内容验收 | 原问 30×3＝90 请求，最多 360 次模型调用；预定追问另最多 30 请求/120 次调用 | 追问名单在冻结前确定，随所属问题族评分 |
| 已知 3 类失败探针 | 9 请求，最多 36 次模型调用 | 不计新增独立准确率样本 |
| 性能批次 | 100 请求，最多 400 次模型调用 | 未过内容门槛不运行；不以成功响应补满而隐去失败 |

累计最多 1399 次模型调用；实际因短路径和提前停止通常较少，此处不是费用预测。任何新增实验、限流失败重跑或补封存集均需更新批次记录与剩余额度；到顶先报告再决定下一轮，不自动超额。若启用付费对照，还受单独获批的金额上限约束，二者先到者停止。

### 测试与交付顺序

1. 新增单元合同和故障反例后，运行完整后端 `pytest scripts/tests/`、类型检查 `mypy scripts/lib/`（采用现有环境/配置），在 `scripts/web/` 运行 `npm test`、`npm run build`；本计划不声称已重跑。
2. 隔离 QA 库、独立 SQLite、受控本机端口回放真实 HTTP/SSE，覆盖追问、取消、超时、重连、引用、保存失败。合规入口、合规索引与跨库哨兵单独回归。
3. 核对模型、源码 SHA、库 manifest、索引/解析器版本、prompt 指纹及 API 实际服务端口；用户看到的入口必须能确认版本，防止再次出现“改了但访问旧服务”。
4. 通过后先交付隔离试用入口和已知限制；取得替换确认再切现用入口。未批准不改 `.env`，不自动重启/发布。模型默认变更单独列明，不夹带供应商切换。
5. 回滚只切代码/模型/库发布指针，不覆盖实时用户会话数据库。新增字段保持前后兼容；不支持兼容时先设计迁移回退，再发布。失败候选保留报告，不反复放宽阈值直至“通过”。

## 7. 人工、费用与停止条件

- **用户/领域人员投入**：关键点确认约 1.5–3 小时，模型对照与最终结果复核另约 2–4 小时，合计先预留 3.5–7 小时，可分批进行；争议或重建封存集另估。自动生成口语变体、整理原文与差异由工具完成，不让用户逐页整理全书或建大型本体。只投入首轮确认也可继续工程/内部体验验证，但未完成结果复核不能宣称专业质量已验收。
- **模型费用**：首选同供应商当前免费候选；执行前复核价格、账号权限、限流和日志数据范围。若免费方案失败，可另提“总额不超过 30 元”的付费对照申请，这是预算上限建议，不是实际费用估算；未批准不调用、不自动 fallback。费用计算涵盖失败、思考/输出及缓存等实际适用项。
- **两轮停止线**：给足正确证据仍不稳定，则不继续无限加问法补丁；给足证据稳定但端到端失败，则只修检索/装配/核对链路；质量过而速度不过，则定位耗时阶段再取舍，不拿流式掩盖错误或慢生成。
- **不纳入本期**：全库法规效力官方核定、全书人工本体、微调、图数据库迁移、默认互联网补充法规、多代理自主循环，以及未获准的 ima 资料上传。现有本体作为可追溯术语/关系辅助，与合规共用概念不意味着共用语料或问答放行规则。

## 9. Constitution Check 与追溯

- [x] **Library-First**：复用现有检索、LLM、图路由和交付组件；引用外部框架实践不等于迁移框架。
